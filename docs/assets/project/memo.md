## 1. AI支援型開発 — 合っています
エンジニアがプロンプトで個別にタスクを指示、それが複数人分いる。体制はAI以前と同じで、一人あたりの生産性だけが上がるという理解でそのとおりです。図版でも第1世代（プロンプト）〜第2世代（コンテキスト）の2世代をまたぐ領域として置いています。md の「既存の開発フローを保ったまま」がまさにこれです。

## 2. 仕様駆動型開発 — 合っていますが、「設計情報を入力」だけだと足りません
アーキテクトが入力し、アジャイルのサイクルで承認を与える／人数は少数、という骨格は合っています。ただこの世代の呼び名はハーネスエンジニアリングで、図版の説明は「ルール・ツール・検証ゲートを設計する」。つまりアーキテクトの仕事は設計情報の入力に加えて、AIが逸脱しないための仕組み（ルール・自動テスト・検証ゲート）を先に作ることです。承認が人力レビューだけでなく、ゲートで機械的に効くようになるのがG2との差です。

あわせて、仕様は入力して終わりではなく設計とコードが双方向で同期し続ける（md 48行目）点も、この世代の中核です。

## 3. ループエンジニアリング — 「エージェントが複数いる」が差分ではありません
複数のAIエージェントが役割分担して動くこと自体は、仕様駆動型でも普通に起こります。**本質的な差は「ループを誰が回すか」**です。

仕様駆動型: 1増分ごとに人間の承認が挟まる（人間がループを回す）
ループエンジニアリング: 実行 → 検証 → 修正 → 再検証 をAI側が自分で閉じる。人間の承認は、各増分ではなくループの設計と終了条件・逸脱時の割り込みに移る
なので「アーキテクトが少数、下位に自律稼働するAIエージェント複数」という絵は結果として正しいのですが、理由は人数構成ではなく承認の粒度が変わることにあります。人間のレビュー能力がスループットの上限でなくなる、というのがこの世代の意味です。

---

補足として、この3つは時系列で置き換わるものではなく、図版でも領域①がG1〜G2を包含する形で重ねています。案件のフェーズによって使い分ける（mdの「単独でも、掛け合わせても」）という位置づけです。

AI人材支援だけはこの世代軸の上にない別軸で、上記どの世代の現場にも人を送り込む領域なので、並べて理解しないほうが整理しやすいと思います。
